# АС «Эксплуатация» — Roadmap разработки

## 1. Назначение

Этот roadmap определяет последовательность разработки АС «Эксплуатация».

Цель — избежать попытки построить всю enterprise-систему сразу и двигаться от устойчивого ядра к промышленной платформе.

Roadmap рассчитан на сценарий:

- 1 основной разработчик / архитектор;
- активное использование Codex и AI-агентов;
- постепенное тестирование на реальных объектах;
- модульный монолит на старте;
- регулярные пилоты;
- расширение после подтверждения процессов.

Сроки ниже являются ориентировочными и зависят от фактической загрузки, качества исходных данных и доступности пользователей для пилота.

## 2. Общая стратегия

# Ориентировочная временная шкала

Для одного человека + Codex:

```text
0–2 месяца
Фундамент + реестр

2–4 месяца
Роли + ТО + первые Work Orders

4–6 месяцев
Дефекты + документы + инвентаризация

6–9 месяцев
Инциденты + изменения + отчёты + пилот

9–12 месяцев
Offline + hardening + расширенный пилот

12–18 месяцев
Промышленная версия

18+ месяцев
Поздние модули
```

Это не жёсткий календарный план.

Главный принцип:

> Каждый этап должен заканчиваться работающей частью системы, которую можно дать реальным пользователям.

# Правила разработки с Codex

## Каждая задача должна иметь

- business context;
- acceptance criteria;
- ограничения;
- роли;
- permissions;
- schema changes;
- API;
- tests;
- UI states;
- audit requirements.

## Codex не должен

- самостоятельно менять бизнес-правила;
- вводить новые статусы без документации;
- делать прямые связи между модулями в обход контрактов;
- удалять историю;
- обходить permissions;
- смешивать domain model и UI model;
- заменять справочники hardcoded enum без причины.

## Обязательные тесты

- unit;
- integration;
- authorization;
- migrations;
- concurrency;
- audit;
- regression.

# Definition of Done для модуля

Модуль считается готовым только если:

1. Есть domain model.
2. Есть миграции.
3. Есть API.
4. Есть permissions.
5. Есть UI.
6. Есть audit.
7. Есть tests.
8. Есть документация.
9. Есть error handling.
10. Есть сценарий ручной проверки.
11. Нет критичных TODO.
12. Модуль проверен на реальных данных.

# Главный контрольный принцип roadmap

Не переходить к следующему крупному модулю, если предыдущий не прошёл реальный пользовательский сценарий.

Правильный цикл:

```text
Спроектировать
↓
Реализовать
↓
Протестировать
↓
Дать пользователю
↓
Собрать обратную связь
↓
Скорректировать
↓
Зафиксировать решение
↓
Идти дальше
```
