# ADR-001 — Модульный монолит как базовая архитектура

- **Статус:** Accepted
- **Дата:** 2026-09-16
- **Контекст:** АС «Эксплуатация»
- **Связанные документы:** `concept.md`, `architecture.md`, `roadmap.md`

## Контекст

АС «Эксплуатация» имеет сложную предметную область:

- объекты;
- оборудование;
- составные инженерные системы;
- ТО;
- работы;
- измерения;
- дефекты;
- ремонты;
- подрядчики;
- инвентаризация;
- инциденты;
- изменения;
- документы;
- риски;
- права доступа.

При этом разработка на первом этапе предполагается небольшой командой, фактически с одним основным разработчиком и активным использованием Codex/AI-агентов.

Многие бизнес-процессы связаны транзакционно. Например завершение ТО может одновременно затрагивать:

- WorkOrder;
- checklist;
- measurements;
- defect;
- asset state;
- asset history;
- audit;
- outbox.

Начало с микросервисной архитектуры увеличило бы:

- инфраструктурную сложность;
- стоимость отладки;
- количество сетевых контрактов;
- количество failure modes;
- сложность distributed transactions;
- требования к DevOps.

## Решение

На первом и основном этапе используется **модульный монолит**.

Backend представляет собой одно логическое приложение ASP.NET Core, разделённое на строгие доменные модули.

Пример модулей:

```text
Identity
Organization
Sites
Assets
Maintenance
WorkOrders
Measurements
Defects
Repairs
Inventory
Incidents
Changes
Documents
Contractors
Qualifications
Notifications
Audit
Reports
Integrations
```

Каждый модуль:

- владеет своими сущностями;
- владеет своей схемой PostgreSQL;
- имеет собственные application use cases;
- публикует контракты;
- не должен напрямую изменять таблицы другого модуля.

## Допустимое взаимодействие

```text
Module A
→ application contract
→ Module B
```

или:

```text
Module A
→ domain/application event
→ Module B
```

## Запрещённое взаимодействие

```text
Maintenance
→ напрямую UPDATE assets.assets
```

или:

```text
Defects
→ напрямую использует Infrastructure другого модуля
```

## Последствия

### Положительные

- проще разработка;
- единая транзакционная граница там, где она действительно нужна;
- проще локальный запуск;
- проще integration tests;
- меньше инфраструктуры;
- легче сопровождение одним разработчиком;
- архитектурные границы можно сохранить даже внутри одного процесса.

### Отрицательные

- требуется дисциплина module boundaries;
- без правил монолит может деградировать в tightly-coupled application;
- при очень большом масштабе отдельные части могут потребовать выделения.

## Эволюция

В будущем допускается выделение сервисов, прежде всего:

- Documents/Media;
- Reports;
- Notifications;
- Telemetry;
- Integrations;
- Search.

Core-домены рекомендуется сохранять вместе максимально долго:

- Assets;
- Maintenance;
- WorkOrders;
- Defects.

## Критерий пересмотра

ADR пересматривается, если:

- независимое масштабирование конкретного модуля становится обязательным;
- deployment одного модуля систематически блокирует остальные;
- изоляция нагрузки требует физического разделения;
- корпоративная инфраструктура вводит обязательный service architecture standard.

## Итог

> Сначала стабилизируем предметную область и границы модулей. Распределённость добавляется только при доказанной необходимости.
