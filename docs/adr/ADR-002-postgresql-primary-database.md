# ADR-002 — PostgreSQL как основная транзакционная СУБД

- **Статус:** Accepted
- **Дата:** 2026-09-16
- **Связанные документы:** `architecture.md`, `database.md`

## Контекст

Система должна хранить:

- 5000+ объектов;
- 500 000+ активов;
- 10 000+ пользователей;
- миллионы WorkOrder;
- десятки миллионов измерений;
- большое количество исторических событий;
- сложные связи и ограничения;
- audit trail.

Ключевые требования:

- транзакционность;
- FK/constraints;
- сложные выборки;
- history;
- JSONB для ограниченных гибких данных;
- возможность partitioning;
- полнотекстовый поиск;
- зрелые backup/PITR механизмы.

## Решение

Основная СУБД:

```text
PostgreSQL
```

PostgreSQL является source of truth для структурированных бизнес-данных.

## Использование

PostgreSQL хранит:

- master data;
- текущие состояния;
- бизнес-историю;
- WorkOrders;
- measurements;
- defects;
- inventory;
- changes;
- incidents;
- audit metadata;
- document metadata;
- integration outbox.

## Не хранится в PostgreSQL

Бинарные документы и фотографии не хранятся как основной способ хранения через `bytea`.

Они размещаются в S3-compatible object storage.

## Причины

- зрелая relational model;
- ACID;
- constraints;
- JSONB;
- pg_trgm;
- FTS;
- partitioning;
- materialized views;
- read replica support;
- зрелая экосистема .NET/Npgsql;
- достаточный масштаб без раннего sharding.

## Альтернативы

### MS SQL Server

Технически подходит, но PostgreSQL выбран как более удобный для Linux/VDS, открытой инфраструктуры и снижения лицензионной зависимости.

### MySQL/MariaDB

Подходит для части задач, но PostgreSQL лучше соответствует требованиям к сложным данным, аналитическим запросам и расширяемости.

### MongoDB как основная БД

Отклонено из-за большого числа строгих связей, транзакционных процессов и требований к referential integrity.

## Последствия

### Положительные

- единый зрелый transactional store;
- удобные migrations;
- возможность масштабировать вертикально и через replicas;
- гибрид relational + JSONB.

### Отрицательные

- требуется дисциплина индексации;
- крупные исторические таблицы потребуют partitioning;
- тяжёлая аналитика позднее может потребовать DWH/read replicas.

## Критерий пересмотра

Пересмотреть, если:

- появляется workload, объективно неподходящий PostgreSQL;
- высокочастотная телеметрия становится отдельным крупным контуром;
- аналитика требует специализированного хранилища.

При этом PostgreSQL остаётся source of truth для core EAM/CMMS данных.
